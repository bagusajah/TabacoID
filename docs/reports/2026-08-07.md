# Daily Report 2026-08-07

## Engineering Question
Dari 98 unsafe shutdowns di NVMe KZ256, berapa yang power loss vs graceful vs kernel panic? Dan bisakah kita bedain dari log yang tersedia?

## Method
- Cek `journalctl --list-boots` untuk riwayat boot
- Cek `last reboot` / `last -x shutdown reboot` dari wtmp
- Grepping syslog dan kern.log untuk shutdown/reboot/panic/power-loss keywords
- Verifikasi NVMe SMART power-loss protection capability (VWC flag)
- Cek ext4 mount options untuk write barrier
- Cek UPS availability

## Findings

### 1. Observability gap: tidak bisa membedakan
| Sumber | Hasil |
|---|---|
| `journalctl --list-boots` | **Hanya 1 boot** — `Storage=volatile`, journal di RAM, hilang setiap reboot |
| `last reboot` | **Kosong** — wtmp mulai fresh `Aug 7 2026` (bar saja di-truncate/rotated) |
| syslog/kern.log | **Tidak ada entry shutdown/reboot/panic** — log hanya menunjukkan operasi normal, kontinu tanpa gap |
| wtmp age | Dimulai dari boot Jul 18, tapi `last` kosong karena file truncated |

**Kesimpulan: dengan konfigurasi saat ini, TIDAK MUNGKIN membedakan power loss vs graceful shutdown vs kernel panic dari log.** Semua history hilang setiap reboot karena:
1. `Storage=volatile` di journald.conf — journal di `/run`, hilang saat power cycle
2. wtmp kosong/truncated setiap reboot
3. syslog tidak persistent across reboot (hanya logrotate, bukan persistent boot record)

### 2. NVMe VWC (Volatile Write Cache)
```
vwci (VWC Present): 1    → Ya, ada volatile write cache
vwc  (VWC Enabled): 0x1 → Enabled
```
NVMe punya volatile write cache yang aktif. Artinya data di cache bisa **hilang** saat unexpected power loss sebelum flush ke NAND. `commit=600` di mount options menambah buffer delay 10 menit, memperbesar window data loss.

### 3. ext4 mount options
```
/dev/nvme0n1p2 on / type ext4 (rw,noatime,errors=remount-ro,commit=600)
```
`commit=600` = fsync delay 10 menit. Tanpa UPS, ini artinya hingga 10 menit data bisa hilang saat power cut.

### 4. UPS
Tidak ada UPS daemon (apcupsd, nut) terinstall. Tidak ada UPS terdeteksi.

### 5. SMART trend (vs laporan sebelumnya)
| Metric | Laporan sebelumnya | Sekarang | Delta |
|---|---|---|---|
| Power On Hours | 5,886 | 5,889 | +3h |
| Unsafe Shutdowns | 98 | 98 | 0 (no new unsafe shutdowns) |

Sistem sudah up 19 hari tanpa unsafe shutdown baru.

## Decision
**Needs Experiment** — dengan observability saat ini, kita tidak bisa menjawab pertanyaan "berapa power loss vs kernel panic". Perlu diaktifkan persistent journal dulu agar boot berikutnya bisa mencatat penyebab shutdown.

## Risk
- `commit=600` tanpa UPS = hingga 10 menit data loss window
- VWC aktif tanpa PLP = write cache content hilang saat power cut
- Setiap power cycle saat ini = blind spot, tidak tercatat penyebabnya

## Recommendations (prioritas)
1. **Ubah `Storage=volatile` → `Storage=auto`** di `/etc/systemd/journald.conf` — journal persistent ke disk, boot berikutnya akan punya riwayat
2. **Turunkan `commit=600` → `commit=5`** atau hapus (default 5 detik) — kurangi data loss window dari 10 menit → 5 detik
3. **Pertimbangkan UPS** — single most effective mitigation untuk 98% unsafe shutdown rate

## Lessons Learned
- `Storage=volatile` di journald.conf membuat root cause analysis impossible untuk shutdown investigation
- NVMe VWC enabled + commit=600 + no UPS = triple risk untuk data loss
- wtmp juga tidak reliable di SBC — bisa truncated oleh logrotate atau reboot
- Tanpa persistent journal, setiap reboot adalah "black box" event

## Next Priority
- Aktifkan persistent journald (config change, 1 baris)
- Turunkan commit=600 → default di fstab (config change, 1 baris)
- Setup SMART snapshot script untuk trend tracking mingguan
