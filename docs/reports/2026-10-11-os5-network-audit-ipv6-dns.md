# OS5 Network Audit: Port Inventory, :53 Listeners, dan Dual-stack Lame Resolution

## Engineering Question

Backlog menyebut "many :53 listeners" yang belum pernah dijelaskan. Log gateway 2026-10-11 juga penuh warning `Dual-stack api.telegram.org path failed (ConnectError)` yang fallback ke IPv4 literal. Dua pertanyaan: (1) apa isi lengkap port listening di Pi dan semuanya dikenali? (2) kenapa koneksi dual-stack ke Telegram gagal berulang?

## Method

Audit read-only: `ss -tulnp` (unprivileged + sudo), identifikasi proses per-port via `ss users:` dan `/proc/<pid>/cwd`, cek `/etc/resolv.conf`, `sysctl net.ipv6.conf.all.disable_ipv6`, grep sumber disable IPv6 di sysctl, resolusi DNS via `getent` + `socket.getaddrinfo`, dan egress test `curl -4 https://api.telegram.org`.

## Findings

**1. IPv6 dimatikan di level kernel — disengaja, via `/etc/sysctl.conf:70-72`:**

```
net.ipv6.conf.all.disable_ipv6 = 1
net.ipv6.conf.default.disable_ipv6 = 1
net.ipv6.conf.lo.disable_ipv6 = 1
```

File terakhir dimodifikasi 2026-08-07. Tidak ada global IPv6 address di interface mana pun. Ini penyebutnya.

**2. Namun Tailscale MagicDNS tetap advertise resolver IPv6.** `/etc/resolv.conf` (generated by tailscale) berisi `nameserver 100.100.100.100` DAN `nameserver fd7a:115c:a1e0::53`. `getent hosts api.telegram.org` balik **IPv6-only**: `2001:67c:4e8:f004::9` — alamat yang mustahil di-connect karena IPv6 off di kernel. Dual-stack client yang menerima AAAA lebih dulu terjebak lame resolution: coba connect ke alamat mati, timeout, baru fallback ke IPv4. Iterasi lain `getaddrinfo` mengembalikan campuran (`149.154.166.110` dulu, IPv6 kedua) — urutan resolver ini nondeterministik, dan itulah kenapa failure-nya intermiten.

**3. Dampak terukur:** log 2026-10-11 mencatat siklus fail-fallback-fail-fallback: 01:58:02 → 01:58:13, ±11 detik penalty per kejadian, kemudian sukses via sticky IPv4 `149.154.166.110`. Dalam 24 jam terakhir tidak ada pesan hilang — mekanisme fallback Hermes bekerja — tapi penaltinya konsisten muncul setiap resolver mengembalikan AAAA duluan.

**4. Mystery :53 SOLVED — benign.** Bukan DNS server liar, hanya `systemd-resolved` stub di `127.0.0.53:53` (tcp+udp), default Ubuntu, loopback-only, tidak exposed.

## Decision

**Needs Human Review** — untuk keputusan enable/disable IPv6:

- **Opsi A (disarankan): hapus 3 baris disable_ipv6 di sysctl.conf + `sysctl -p`.** Risk rendah: jaringan LAN/router punya IPv6, Tailscale sudah berbisnis dengan IPv6, dan ini menghilangkan root cause. Perlu verifikasi lanjutan bahwa tidak ada service yang justru rusak saat IPv6 aktif (openvpn config, docker daemon).
- **Opsi B (mitigasi minim): matikan AAAA di resolver** — karena resolv.conf dikelola Tailscale, caranya accept-dns=false + resolv.conf statis, atau `filter-AAAA` di systemd-resolved. Lebih ribet, tapi tidak mengubah postur jaringan.
- **Opsi C (do nothing):** biarkan fallback jalan. Penalti ±11s intermiten, tidak ada data loss teramati.

Saya tidak mengubah konfigurasi jaringan autonomously — ini menyentuh semua koneksi host (openvpn server, docker, jellyfin) dan butuh mata user.

## Risk

Opsi A: service yang selama ini "aman" di belakang IPv6-off bisa expose behavior baru (mis. docker binding ke ::). Mitigasi: uji di jam santai, `docker ps` + port scan ulang setelah enable. Opsi C: penalty 11s berulang tiap resolver nondeterminism, dan sticky-path juga kadang gagal (log 02:49) sebelum re-walk.

## Lessons Learned

- "Many :53 listeners" dari backlog ternyata satu stub systemd-resolved — signal lama yang belum pernah diverifikasi. Audit kecil, jawaban definitif.
- Lame resolution dual-stack adalah kelas failure yang halus: resolver tidak salah, kernel yang dibisukan — gejalanya intermiten dan mudah disalahkan ke jaringan.
- `disable_ipv6=1` di sysctl adalah band-aid umum yang menciptakan mismatch dengan resolver advertise AAAA.
