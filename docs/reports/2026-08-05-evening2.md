# Daily Report 2026-08-05 (Evening Cycle)

## Engineering Question
"Seberapa reliabel token refresh di webreader? Apakah TICMI 'Over Limit User Login' menyebabkan data loss atau hanya warning kosong?"

## Method
Analisis Docker logs webreader-api (3 hari) — extract semua token refresh events (success/failure), cross-reference dengan nginx access logs untuk melihat apakah API request yang masuk SETELAH refresh failure tetap berhasil. Baca source code `tokenManager.ts` untuk memahami error handling.

## Findings

### 1. Token Refresh Pattern (3 hari)

| Timestamp (UTC) | Event | Note |
|---|---|---|
| 08-02 17:01 | ✅ refreshed | limitId 2325 |
| 08-03 01:01 | ✅ refreshed | limitId 2327 |
| 08-03 09:01 | ✅ refreshed | limitId 2335 |
| 08-03 ~17:01 | ❌ Over Limit | 1st failure |
| 08-03 ~01:01+ | ❌ Over Limit | 2nd failure |
| (repeat...) | ❌ Over Limit | 3rd failure |
| 08-04 14:02 | ✅ refreshed | Setelah container restart, limitId 2341 |
| 08-04 ~22:02 | ❌ Over Limit | 1st failure |
| 08-05 ~06:02 | ❌ Over Limit | 2nd failure |
| 08-05 ~14:02 | ❌ Over Limit | 3rd failure |

**Pattern:** TICMI mengizinkan ~3 concurrent refresh sessions. Setelah 3x sukses, semua scheduled refresh gagal dengan "Over Limit User Login" sampai container restart (yang trigger logout → free session slot).

### 2. Impact pada API Requests

**Tidak ada data loss.** Semua API request yang masuk SETELAH token refresh failure tetap return 200. Ini karena:

1. Scheduled refresh gagal → `cachedToken` tetap ada (tidak di-clear pada failure)
2. API request berikutnya pakai `cachedToken` yang masih valid
3. Token hanya di-refresh ulang ketika upstream return 401 (on-demand refresh)
4. TICMI token lifetime >> 8 jam refresh interval

**Bukti:** 40 request via nginx logs — 0 error (kecuali 404 untuk unimplemented routes).

### 3. Nginx Response Code Distribution

404s berasal dari unimplemented routes (`/v1/ticmi/ihsg`, `/v1/ticmi/listed-companies`, `/v1/ticmi/sector-indices`) — bukan token issue.

### 4. Container Reliability

| Metric | Value |
|---|---|

| Docker image | Healthy |

### 5. Root Cause: TICMI Concurrent Session Cap

TICMI membatasi jumlah concurrent session per user. Setiap `loginOnce()` membuat session baru **tanpa logout session sebelumnya**. Setelah ~3 session menumpuk, cap tercapai.

Source code `tokenManager.ts` line 219-226:
```
refreshToken(reason) → loginOnce() → cachedToken = new token
```

**Tidak ada logout-before-login pada scheduled refresh.** Logout hanya terjadi saat container shutdown (`shutdownTokenManager`). Artinya setiap 8 jam, session baru dibuat tanpa menghapus session lama.

## Decision
**Needs Human Review** — sistem resilient (tidak ada data loss), tapi ada dua hal yang perlu keputusan:

1. **Tambahkan logout-before-login di scheduled refresh?** Ini akan fix "Over Limit" tapi menambah latency setiap refresh (2 HTTP calls vs 1). TICMI session timeout-nya berapa lama? Kalau >24 jam, logout-before-login tidak perlu — cukup ignore refresh failures.

2. **Unimplemented routes (22% 404)** — apakah `/ihsg`, `/listed-companies`, `/sector-indices` perlu diimplementasi atau dihapus dari cron callers?

## Risk
Risiko rendah — `cachedToken` tetap valid, on-demand refresh pada 401 menangkap token expiry. Worst case: scheduled refresh gagal terus, tapi sistem tetap jalan sampai token expired dan 401 trigger refresh.

## Lessons Learned
- TICMI "Over Limit User Login" bukan data loss risk — cached token tetap serve request
- Scheduled refresh tanpa logout menumpuk session — pattern yang perlu diperbaiki kalau TICMI memperketat session cap
- 22% nginx 404 dari unimplemented routes — noise di log, bisa dihapus atau implementasi
- `tokenManager.ts` error handling sudah bagus: dedup concurrent logins, boot backoff, graceful failure

## Next Priority
- Investigasi TICMI session timeout duration (berapa lama session expired sendiri?)
- Pertimbangkan logout-before-login di scheduled refresh
- Implement atau hapus unimplemented TICMI routes
